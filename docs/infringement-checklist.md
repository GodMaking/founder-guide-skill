# 侵权对比证据清单

本文用于判断“疑似盗版”与“独立开发”的区别，并整理可提交给平台的对比材料。

> 结论先行：**不能因为别人也写了一个创业 Skill、用了相同的书或相同的方法论，就认定侵权。** 著作权保护具体表达，不保护思想、方法、概念、功能。是否侵权，由平台或司法机关依据证据判断。

## 1. 先做三个判断

### 判断一：对方是否在商业使用

对照 [COMMERCIAL-LICENSE.md](../COMMERCIAL-LICENSE.md)：

- 在闲鱼、淘宝、抖音、小红书、知识星球等渠道收费
- 用于付费课程、付费社群、付费咨询、付费代做
- 打包进付费软件、SaaS、工具站、课程、模板包
- 企业内多人商业使用但未取得团队/企业授权

如果对方只是个人学习、非商业分享，并保留了 LICENSE 与 `Required Notice`，通常属于非商业许可允许的行为，不应按盗版投诉。

### 判断二：对方是否复制了具体表达

需要看代码、文档、模板、案例、目录结构、独特措辞，而不是只看“功能像不像”。

### 判断三：是否存在独立开发可能

如果对方能说明独立创作过程，且具体表达明显不同，即使功能相似，也可能不构成侵权。

## 2. 代码对比

| 对比项 | 怎么比 | 证明力 |
|---|---|---|
| 文件树与目录名 | `tree` / `find` 对比 | 中 |
| 文件名与函数名 | `diff -r`、IDE 对比 | 中 |
| 代码逐行相同 | `diff -u`、哈希 | 高 |
| 注释、日志、错误提示相同 | 搜索独特句子 | 高 |
| 变量命名、参数顺序相同 | 人工比对 | 中 |
| 相同 bug / 相同边界错误 | 运行对比 | 高 |
| 相同测试数据 / 示例数字 | 搜索 | 高 |
| 提交时间线 | Git log / 平台发布时间 | 高（结合其他证据） |

示例命令：

```bash
# 对比两个目录
diff -ru original/ suspected/ > diff.txt

# 计算文件哈希
shasum -a 256 original/skills/founder-guide/scripts/startup_calc.py
shasum -a 256 suspected/scripts/startup_calc.py

# 搜索独特句子
rg -n "替代方案成本 ÷ 你的成本" original/ suspected/
```

## 3. 文档与内容对比

| 对比项 | 例子 | 证明力 |
|---|---|---|
| README 结构与小标题 | 同样的章节顺序、同样的表格 | 中 |
| SKILL.md 的独特措辞 | “判断器，不是书库”“一次一本一条” | 高 |
| 决策卡字段与格式 | 同样的字段顺序、同样的示例数字 | 高 |
| 参考文档的段落 | 大段相同或仅换同义词 | 高 |
| 书目索引的选择与排序 | 47 个编号、同样的分类与取舍 | 中 |
| 案例的数字与情节 | 同样的 3,500 / 399 / 10.3 件 | 高 |
| 模板文件 | 同样的表头、占位符、提示语 | 高 |
| 错别字 / 独特比喻 | 同样的错误或同样的比喻 | 高 |

“换同义词”“调整段落顺序”“改几个数字”不等于独立创作。要逐段标注相同点。

## 4. 素材与视觉对比

- 同样的封面、配色、排版、图标
- 同样的截图、演示数据、案例图
- 同样的文件名、目录结构、压缩包结构
- 同样的版权页、授权编号格式、水印

如果对方直接打包了本仓库，通常会保留大量原始文件与目录名，这类证据比较容易固定。

## 5. 时间线对比

需要证明“原作在先，对方在后”：

- 本仓库首次提交时间与哈希
- 被侵权版本的 tag / Release 时间
- 对方商品发布时间、详情页截图时间
- 对方交付文件的创建/修改时间（如可获得）
- 公开文章、视频、课程的上线时间

时间线只能作为辅助证据。对方可能主张“独立更早创作”，所以要和具体表达对比结合使用。

## 6. 接触证据

公开仓库意味着任何人都有接触可能，但“有机会接触”不等于“实际复制”。更有力的接触证据包括：

- 对方曾购买、下载、咨询、加入社群
- 对方交付物包含本仓库的授权编号、水印、版权页
- 对方交付物保留了本仓库的 `Required Notice`、文件路径、注释
- 对方在聊天/商品页中使用本仓库的独特表述

如果对方只是看过公开仓库，然后独立重写，且表达不同，不能仅凭“看过”认定侵权。

## 7. 独立开发的抗辩

以下情况需要谨慎，不宜直接投诉：

- 使用相同的公开书籍、相同的创业概念、相同的行业术语
- 实现类似功能，但代码、文档、结构、措辞明显不同
- 采用相同的通用方法（如 SWOT、单位经济、runway），但这些方法本身不受著作权保护
- 对方能提供独立的创作记录、草稿、提交历史
- 对方使用的是公共领域、开源许可允许的素材

**不要**把“功能相似”“主题相同”“都提到同一本书”当成侵权证据。

## 8. 相似度分级与建议动作

| 级别 | 表现 | 建议 |
|---|---|---|
| A. 高置信 | 大量代码/文档逐字相同；保留原始文件名、注释、错误；时间线在后 | 固定证据，提交平台投诉；必要时发律师函 |
| B. 中置信 | 结构、案例、措辞高度相似，但有改动；有接触证据 | 补充对比表，先与对方沟通或平台投诉 |
| C. 低置信 | 仅功能、主题、方法论相似；表达不同 | 不建议按侵权投诉；可关注是否冒用作者名义 |
| D. 合规使用 | 非商业使用，保留 LICENSE 与 Required Notice | 不属于侵权；如需 commercial 使用，引导购买授权 |

## 10. 投诉前自检

逐条回答，任何一条答不上来就先补证据：

- [ ] 我是否拥有该作品的著作权？
- [ ] 我能否证明原作首次公开时间早于对方？
- [ ] 我是否保存了对方商业销售的证据？
- [ ] 我是否做了具体表达对比，而不是只说“很像”？
- [ ] 我是否排除了非商业许可允许的使用？
- [ ] 我是否考虑了对方独立开发的可能？
- [ ] 我是否避免了披露买家个人隐私？
- [ ] 我是否只陈述可核实的事实，没有夸大？
- [ ] 我是否保存了投诉编号与平台回复？

## 11. 边界

- 公开源码不能从技术上阻止复制
- 平台投诉是否成立，由平台依据证据判断
- 著作权保护表达，不保护思想、方法、概念
- 独立开发类似功能不一定侵权
- 恶意投诉、虚假投诉可能承担法律责任
- 涉及较大金额或反复侵权时，建议咨询律师
